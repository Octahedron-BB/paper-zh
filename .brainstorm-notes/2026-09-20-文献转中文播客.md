**一句话**：把英文综述 PDF 变成「中英对照全译（供看）+ 中文口语讲稿（供听）」，
并为将来的「音频 ↔ 原文定位」预留段落锚点。

**已经能用了**：4 篇不同期刊跑通全链路、0 失败。
- 分段结构全对、无文字丢失 → `src/segment.py`
- 轨A 全译 / 轨B 口语稿 → `data/translation/`、`data/script/`
- 中英交错对照（推荐阅读形态）→ `data/interleave/`，VS Code `Ctrl+K V` 打开
- 六项 QA + 两套离线测试（`test_core.py` 18/18、`test_segment.py` 8/8）

**下一步（按重要性）**
1. **轨B 讲稿人工通读** ← 唯一从未被验证的东西，机器只能证明结构完整
2. README 固化新文献三步工序：`check_terms` → `disambiguate` → `run_pipeline`
3. TTS + 段落时间戳（最后一层，不影响任何上游缓存）

**硬约束（别违反）**
- **只自己用**。三条红线：① 任何"向公众提供" ② 全文进第三方云服务 ③ 绕过付费墙
- 仓库**只放工具**：不含 PDF、不含译文/讲稿（已在 `.gitignore` 里）
- 改 prompt 必须递增 `*_VERSION`；改分段逻辑必须递增 `SEGMENTER_VERSION`
  —— 否则缓存会**静默**复用旧结果，表现为"改了代码但没变化"

**三条必须知道的设计（不读正文也要记住）**
1. **术语 `mode` 决定改动成本**：`hard_replace` 免费（译后字符串替换、立刻生效）；
   `prompt_hint` 只失效命中段。原则：**能用字符串替换解决的绝不调 LLM**。
2. **`zh` 只放译名，解释放 `note`**。`zh` 的字面写法是最强指令——把解释塞进去，
   会被整串照抄到句子里（SIF 就因此重复了 12 次）。
3. **检查器的判据本身要先验证**。本项目我产生过 **5 次不实结论**，
   每次都是"先打印原始数据 / 先查 git"这一步救回来的。

**换新期刊时先怀疑什么**：分段器的问题几乎全部来自**"写死绝对值"**。
见「跨期刊泛化实测（修掉的 6 处硬编码判据）」和「截断标题的真实成因（四个机制）」两节。

### 信号三层判断

- 【有人需要】✅ 较充分（供给侧在投入 + KOL 反复谈"通勤听论文"；期刊已把 AI 播客做成固定栏目，如《国际医学放射学杂志》2026 年 2–3 月多期）。
- 【有人付钱】⚠️ **弱**。已证实的付费场景是"带我读懂/答疑/帮我发论文"（知识星球 399 元/年、训练营 1499 元、7 天医生营 1000+ 人）。
  **"读给我听"本身没有任何独立收费证据**（文献鸟未取到单独定价；淘宝代读：未找到）。
- 【有增长】⚠️ 部分（机构级在投入 = 品类形成期），但缺趋势数据（小宇宙不可检索）。

### 明显未被覆盖的空缺（✅ 调研结论）

1. **没有面向"高密度综述"（Nature Reviews 级）的专项优化** —— 全是通用 PDF 处理，密集机制图/数据表/缩写体系一律当纯文本。
2. **中文垂直产品是空的**（豆包/ima 是通用文档工具；唯一的活跃中文开源项目停更两年）。
3. **没有"期刊/学科维度的持续音频流"**（都是单篇、自托管）。

### 版权 / 合规（⚠️ 这是本方向最硬的一堵墙）

- Nature Reviews 属**订阅/混合期刊**（非完全 OA），期刊页明确"All such rights are reserved"。
- nature.com 条款（版本 2025-12-15）明文**允许**：私人非商业浏览/收听/偶发打印；**禁止**：商业使用、"distribute, transmit, … or otherwise make available"任何内容、**"copy, download, or store … to populate a database"**。
  → **注意：把论文全文送进第三方云服务（云 TTS / 大模型 API）本身就落入"向第三方提供"与"填充数据库"两条**，即使用户只是自用。这是做"程序"时必须先设计的架构约束（本地推理 vs 云端 API 是合规问题，不只是成本问题）。
- Springer Nature TDM 政策：机构授权、非商业研究、限速 1 req/s（个人可下载）、API key 150 req/min；要求内容**仅项目期间、存内网、第三方不可访问** → 与"做成公开播客"直接冲突。商业 TDM 需付费。`tdm@springernature.com`
- 中国《著作权法》：翻译权（第 10 条）+ 制作录音制品（第 16、42 条需**双重许可 + 付酬**）+ 信息网络传播权（第 10 条）；合理使用仅第 24 条第（一）项"个人学习研究欣赏"可援引。
- 平台：Apple Podcasts 1.7 要求"权利自证"、1.11 要求 AI 生成内容**显著披露**；小宇宙 4.2 要求上传者保证不侵权，侵权即移除并自负责任。
- **可直接合法（翻译+音频+公开）的来源清单**：CC BY / CC0 / 公有领域（Nature Communications、Scientific Reports、BMC、npj、PMC OA 子集、MMWR 等美国政府出版物）→ 仅需署名与标注改动。**arXiv 默认许可不可再利用**（须逐篇看）；CC BY-ND 不得翻译。
- 风险分级：**私人自用=低（灰色）** / 免费发给少数同事=中 / **公开免费播客=高** / **收费=极高**（法定赔偿上限 500 万，可 1–5 倍惩罚性）。
- 红线三条：① 任何"向公众提供"；② 全文进第三方云服务；③ 绕过 DRM/付费墙。
- 合法替代路径：只用 CC BY/公有领域 → 申请 RightsLink/出版社授权 → 做"解读/评论"只适当引用（第 24 条第（二）项）→ 无障碍用途（第 24 条第（十二）项）→ 用官方 Nature Podcast。

## 查证发现（第二轮 · 数据源与 TTS 选型，2026-09-20）

### 数据源：网页 HTML vs PDF —— 实测结论

**A. nature.com 网页 HTML 的真实结构（✅ 子代理用浏览器实测 DOM，含用户给的那篇文章）**
- ✅ 有**章节级锚点**：`<h2 id="Sec1">`、容器 `div#Sec1-content`、`#Abs1-*`、`#Bib1-*`、`#Ack1`；图 `div#figure-1` / `#figure-1-desc`；表 `#Tab1`。
- ❌ **没有段落级 id**：两篇 OA 文章的 `id="Par\d+"` 计数均为 **0**，正文段落就是裸 `<p>`。
  （注：Nature 早期模板曾有 `Par{n}`，改版后消失 → 依赖官方段落 id 的方案不可靠）
- ✅ 唯一有段落级 id 的是参考文献条目：`<p class="c-article-references__text" id="ref-CR1">`。
- ⚠️ **付费墙文章静默只给 Abstract**：未订阅时页面只剩 `Abs1` + `Bib1` + 5 张图，**不报错**，`Sec*` 数量为 0 → 必须写"付费墙检测"，否则会拿到一篇"假的全文"。
- ⚠️ 登录墙：直接请求会被 302 到 `idp.nature.com/authorize?...`（无 Cloudflare 挑战，但需要维持登录 cookie）。
- robots.txt：**没有** `Disallow: /articles/`，也没有 Crawl-delay；被禁的是 `/search`、`/*/figures`、`/*/tables`、`/*/metrics` 等。
- 条款里那句"populate a database"后面**其实留了 fair dealing 的例外**（UK CDPA 1988）→ 私人自用属灰色但低风险。

**B. Springer Nature 官方 API（正规军路线）**
- ✅ `api.springernature.com/openaccess/jats` → **JATS 全文 XML**，但**只覆盖 OA 文章**（Nature Communications / Scientific Reports 等）。
- ✅ `api.springernature.com/xmldata/jats`（Full Text API/TDM）→ 订阅全文，但需 **"special agreement"/机构 TDM License**，个人自助注册能否开通 **❓ 官方文档未说明**；且官方措辞 `where available` 说明**不保证覆盖指定那篇 Nature Reviews**。
- ✅ 旧 host `spdi.public.springernature.app` 已于 2026-08-07 退役。
- 结论：**对"个人自用 + Nature Reviews 订阅刊"这条基本走不通**（除邮件 `tdm@springernature.com` 个案询问）。

**→ 关键反转：网页抓取不是更优解，PDF + GROBID 才是。**
- 用户想走网页的动机是"怕 PDF 抽取乱"。但实测显示网页路线**恰好缺了用户最需要的段落级定位**（没有 `Par{n}`），且要维持登录会话、页面改版即失效、付费墙静默失败。
- 而 **GROBID 反而天然提供段落级结构 + PDF 坐标**。

**C. GROBID（✅ GitHub 实测）**
- `grobidOrg/grobid`：**5133★**，Apache-2.0，最近提交 **2026-09-17**（活跃），生产级（ResearchGate / Semantic Scholar / HAL / CERN 在用）。
- 输出 **TEI XML**：section / **paragraph** / figure / table / reference marker 全有标签，共 68 类。
- ⭐ **带 "PDF coordinates for extracted information"** → 可做 **音频时间段 ↔ 段落 ↔ PDF 页面坐标** 三向对齐（这正是用户要的定位功能的技术底座）。
- ⚠️ 坑：源码构建需 OpenJDK 21；官方明说"**cannot ensure support for Windows**" → **Windows 上必须走 Docker**；默认只启 CRF，DL 模型需 Python 3.10–3.11 + JEP。参考文献解析 F1 ≈ 0.87（约 13% 出错）。
- 备选：MinerU **80,261★**（2026-09-19）、Docling **67,039★**（2026-09-18）、marker **39,848★**（2026-09-13）、pdfplumber 10,756★、PyMuPDF 10,742★（⚠️ **AGPL-3.0**）。
- ❓ 未实测：MinerU / Docling / marker 在"双栏 + 公式 + 表格"上的具体强弱差异 —— **需在本工作区跑同一篇 PDF 做基准测试**。

### TTS 选型：把"不枯燥"做出来

**⭐ 最重要的判断（🧠）："不枯燥"的解法主要不在 TTS，而在文本。**
- 用最贵的 TTS 念一篇翻译腔书面语，照样催眠；把文本先改写成**口语讲解稿**，用普通 TTS 也听得下去。**文本占 80%，音色占 20%。**

**长文工程硬约束（✅ 有硬证据）**
- **自回归 TTS 无法一次合成 1 万字，必须分段**：Qwen3-TTS GGUF 作者给出公式 `ctx ≈ 10 + 16.5 × 音频秒数`，**每路 512 ctx 只够约 30 秒**，超出直接丢后续文本（`Talker context overflow`）。
- 分段的副作用：**音色漂移 / 语气基线跳变 / 段间停顿突兀**。缓解：复用参考音频 prompt + 固定随机种子 + 段落边界切在句末 + 固定时长静音。
- **术语发音是必须做的预处理**，否则听感立刻崩：`IL-6`→"白介素六"、`5-HT2A`、`α-synuclein`、`p < 0.05`、`n = 128`（易读成"一二八"）、`μg/mL`。三层做法：① 正则/词典改成中文读法；② 模型自带注音接口；③ 用 LLM 整篇归一化（abogen 已产品化）。
- 现成外壳可参考：`abogen` 6,025★（MIT，PDF/EPUB→音频+同步字幕，引擎 Kokoro）、`TTS-Story` 336★（**有 chunk 复核与单段重生成**，长文容错关键）。

### ⚠️ 三个必须先解决的坑

**坑 1：上标引用号会污染正文文本流（这是我最开始没想到的）**
- 实测样本：`its power to distract23,58–65 (Fig. 2c)`、`(BA 25, also known as the subgenual ACC)23.`
- 引用号**不是丢了，而是黏在词尾混进正文**。不处理 → LLM 会当成内容、TTS 会念成"二十三点五十八到六十五"。
- ✅ 好消息：上标是**独立 span**（size 4.5–5.6pt，远小于正文 8.2pt）→ **可在 span 层按字号精确剔除**，
  不需要在字符串层用正则猜。这是 PyMuPDF（带版面信息）相对"纯文本"的关键优势。
- （自我纠错：我第一轮曾怀疑"丢字"（空引号），复核后 **否定了** —— 空引号/空括号检测均为 0 次。不是丢字，是污染。）

**坑 2：纯文本切不出段落** ⚠️ 直接影响"分段翻译"可行性
- 空行启发式只切出 **21 段**，平均 **668 词/段**，最长 **1,102 词** → 粒度完全不可用。
- 原因：PDF 靠**首行缩进 + 行距**分段落，**没有空行**。所以"按段落切分"拿不到现成边界。
- → **"分段翻译"这个需求的真正难点不是调用 LLM，而是"段落边界从哪来"**。必须靠：坐标缩进检测 或 GROBID。

**坑 3：页眉每页重复**（清洗即可，成本低）

### 翻译层设计判断（待与用户确认）

**判断 1：翻译不该是一层，应该是两层**
- **轨 A 对照译文**（忠实翻译，供"看"）；**轨 B 口语讲稿**（供"听"）。两层共享同一 paragraph ID → 定位功能对两轨都成立。
- 理由：讲稿为了好听懂**必然损失精度**。举例（真实句子）：
  - 原文：*These unique elements of mental control suggest that hippocampal disinhibition is a transdiagnostic factor underlying intrusive thinking, linking the fronto-temporal control pathway to preclinical models of psychiatric disorders and fear extinction.*
  - 直译朗读："这些心理控制的独特要素提示，海马去抑制是侵入性思维背后的一种跨诊断因素，将额颞控制通路与精神疾病的临床前模型及恐惧消退联系起来。" → 一句 38 字，听的人接不住。
  - 讲稿："这里有个关键推论：海马一旦失去抑制，侵入性思维就会冒出来；而且这个机制跨多种精神疾病都存在，不是某一种病专属。所以这条额颞通路可以直接和动物模型里的恐惧消退研究对接。" → 好懂，但"preclinical models"被淡化成"动物模型"，"transdiagnostic"的解释也变了。
  - → 所以**两层 + 定位**是一个整体设计：讲稿负责"听得下去"，译文 + 原文定位负责"随时能查证"。
- 若合成一次调用（翻译+口语化），改术语或改语气会互相牵连，缓存全废。

**判断 2：缓存 key 的正确设计（用户想要的"改术语只重译相关段"）**
- ❌ `hash(段落原文)` —— 改术语后译文过期却不会失效
- ❌ `hash(段落原文 + 整个术语表)` —— 改 1 个词 → 全篇失效，正是用户想避免的
- ✅ **`hash(段落原文 + 该段实际命中的术语条目子集 + 模型 + prompt 版本)`**
  → 改一个术语，只有**真正包含该术语的段落**变脏，精确重译。

**判断 3：改术语多半根本不需要重译 LLM** ⭐
- 中文有个天然优势：术语替换**近乎无损**（无性/数/格变化，不牵动冠词与词形）。英文换词要改句子，中文经常直接换就行。
- → 术语表分两类：
  - `hard_replace`：译后**字符串替换**，0 token、0 延迟；`inhibitory control` → `抑制控制` 这类。
  - `prompt_hint`：必须进 prompt 的（歧义澄清、译者注、需要改句结构的）。
- 原则：**能用字符串替换解决的，绝不调 LLM。**

**判断 4：术语表要"先发制人"，不要"亡羊补牢"**
- 用户设想的场景是"听着听着发现不对再改" —— 被动、代价高。
- 更好：首次翻译**之前**先让 LLM 从全文抽术语候选（一次便宜调用），用户一次性审 50–100 个词定死译法。
- ⭐ 更强的点：**术语表是可以跨文献复利的资产**。读同领域第二篇、第三篇时直接继承。
  → 长期看，"积累的私人术语表"比"音频"更有价值，也是这个项目真正的护城河。

**判断 5：省 token 不是做段落缓存的理由** ⚠️（用户的动机需要纠正）
- 算账：正文 14,093 词 ≈ 19k input token；中文译文输出约 20k token → **一篇约 4 万 token**。
  按当前主流 API 价格折算，**一篇成本是"几分钱"量级**。
- 所以"全跑一遍浪费 token"**在钱上不成立**。
- 真正值得做段落级缓存的理由（按重要性）：
  1. **保住用户人工校订过的成果** —— 这是钱买不到的稀缺资源；
  2. 保证术语与语气的一致性（整篇重跑会漂移）；
  3. LLM 输出非确定性 → 全重跑会让**本来没问题的段落随机变差**。
- → 这改变设计优先级：缓存要**持久化 + 可 diff + 可回滚**，而不是"为了省钱的分块"。

### 两个核心设计（本项目的技术核心）

**① 术语表分两类，决定"改动的成本"**
- `hard_replace`：译文生成后的**字符串替换**。改它 **0 token、0 段重译、立刻生效**。
  依据：中文无性/数/格变化，术语替换近乎无损（英文换说法常需重构句子，中文经常直接换词）。
- `prompt_hint`：必须进 prompt 的（歧义澄清、需改句结构）。改它 → **只重译命中的段落**。

**② 缓存键 = sha256(模型 | prompt版本 | 原文hash | **该段命中的 prompt_hint 术语**)**
- ⚠️ 我在写代码时发现自己的初版设计有矛盾并当场修掉：**`hard_replace` 类绝不能进缓存键**，
  否则"改它零成本"这个设计就白费了。（对应用例见 `test_hard_terms_are_excluded_from_cache_key`）

## 同名异义（用户提问）—— 设计与实现（2026-09-20）

**用户提问**：同一个词/缩写在不同文章意思不同怎么办？（"虽然可能不常见"）
**判断**：这个担心是对的，而且在生物医学里**很常见**。它是最危险的 bug 类型，因为：
- 事前想不到（你不会记得 MSN 在别处是中棘神经元）
- 事后极难发现（译文完全通顺，只是全篇错了）
- 代价不对称（改一个术语可能触发 40+ 段重译）

### 解法一：术语条目加**作用域**（scope），就近覆盖
```
global          个人偏好，永远这么译
field:<学科>    只在某学科域生效，如 field:neuroscience
doc:<文档ID>    只在这一篇生效（写进 glossary-d/<文档ID>.yaml）
```
解析优先级 **doc > field > global**。原则：**主表保持干净、可跨文献复用**，
某篇的特殊含义只写在该篇的覆盖文件里。
**同级出现两种译法 → 直接报错中止，绝不静默挑一个。**

### 解法二：**自动发现**冲突，不靠用户预先想到
学术论文有强惯例：缩写首次出现必给全称 `全称 (ABBR)` / `ABBR (全称)`。
**这是纯正则能抽的，不需要 LLM。**

实现要点（`src/abbrev.py`）：
1. 正则找候选 → 2. **最小后缀裁剪** → 3. **首字母校验**
   - 「最小后缀裁剪」是关键：PDF 抽出的文本没有段落边界，正则容易把整句吃进来
     （如 `suggests that suppressing the medial septal nucleus`）。
     做法：**从右往左贪心**吃掉首字母匹配的词，吃完所有字母就停，左侧一律丢弃。
     这个方法一次性修掉了 `as in post-traumatic stress disorder`、
     `measured as stop signal reaction time` 等我原本打算用黑名单硬顶的情况。
   - 「首字母校验」：缩写必须是全称有效词首字母序列的子序列（虚词跳过）
4. **不猜，靠声明**：术语表条目可填 `full_en`（缩写英文全称）→ 与本文定义做**精确比对**。
   不填就只能靠中文译法反推英文，**必然全是误报**（初版就是这么错的）。

### 真实案例（已落地）
**MSN**：神经科学里默认是 medium spiny neurons（中型棘状神经元），
但本文指的是 **medial septal nucleus（内侧隔核）**，出现 11 次。
- 主表 `glossary.yaml`：`MSN → 中型棘状神经元, scope: field:neuroscience`
- 单篇覆盖 `glossary-d/s41583-025-00929-y.yaml`：`MSN → 内侧隔核, scope: doc:s41583-025-00929-y`
- 结果：本文解析出 **内侧隔核** ✅；读别的文献自动回落到"中型棘状神经元" ✅

### 顺带捞出的漏网术语（这正是审计工具的价值）

### ⚠️ 我在这轮踩的两个坑（都值得记住）

   根因：贪心循环在**吃完所有字母后没有 `break`**，遇到下一个实词就误判失败。

## 术语替换的两个真 bug + 一个我自己引入的 bug（2026-09-20 修复）

用户确认：**口语化保留**（轨B 现有的轻微"编辑性添加"可以接受）。

### Bug 1：`hard_replace` 只替换 aliases，不替换英文原词本身 ⭐
初版 `apply_hard_replace` 只做 `aliases -> zh`。**如果 LLM 把英文缩写原样保留（如 DLPFC），
这条规则就完全不生效** —— 本文的 DLPFC 全篇没被翻译，就是这么漏的。
→ 修复：替换四类 ①括号内冗余缩写 ②带前缀变体（aDLPFC） ③**英文原词本身** ④同义别名。
→ 💡 逃生口：若想保留英文缩写不译（中文医学文献常见做法），把该条 `zh` 设成缩写本身即可，
  此时 ②③ 自动变成无操作。

### Bug 2：方位前缀变体匹配不到 ⭐（用户直接问到了这句）
`aDLPFC` / `rDLPFC` / `lVLPFC` 这类"方位前缀 + 缩写"写法在神经科学里极常见，
但初版正则用 `(?<![A-Za-z])DLPFC(?![A-Za-z])`，**前缀的 `a` 挡住了词边界** → 匹配不到。
→ 修复：缩写允许一个**小写**方位前缀（`(?-i:[a-z])?`，强制小写以免把 ADLPFC 也当中）；
  并加 `PREFIX_ZH` 映射（a=前部 / r=右侧 / l=左侧 / d=背侧 / v=腹侧 / m=内侧 / p=后部 / c=尾侧 / s=上）。
  效果：`向右aDLPFC发出信号` → `向右前部背外侧前额叶发出信号`，残留 `aDLPFC` 0 次。

### Bug 3（⚠️ 我在修复 Bug 1 时自己引入的）：括号删除丢信息
初版规则是**无条件删除** `（ABBR）`，目的是避免「背外侧前额叶（背外侧前额叶）」这种重复。
但英文 `Action stopping indices (SSRT)` 译成「动作停止指标（SSRT）」时，**括号前并没有中文译名**，
删掉就把 SSRT 整个丢了 —— 这是**静默丢信息**，比译错更危险。
→ 修复：**仅当括号前 40 字符内已出现中文译名时才删**；否则把缩写换成中文
  （`动作停止指标（SSRT）` → `动作停止指标（停止信号反应时）`）。

### 顺带补上的设计缺口：轨A **没有**完整性体检
轨B 有"信息保全率"，但轨A 没有等价检查 —— 而**轨A 漏译比轨B 概括更危险**（对照时才看得出，听不出来）。
→ 新增量法：**中文/英文词比值**。实测本文 62 段区间 **1.87–2.59，中位 2.28**，分布很窄 → **无一段漏译**。

### 另一个设计改进：raw / final 分离，让 hard_replace 对**两条轨都免费**
轨B 的缓存键原本基于轨A 的**最终**译文 → 改一个 hard_replace 术语会把 62 段讲稿全部作废。
→ 修复：轨A 同时保存 `zh_raw`（替换前）与 `zh`（替换后）；**轨B 以 `zh_raw` 为键**并对输出做同样的替换。
  效果：本次修复后重跑，**124/124 全部命中缓存、0 次 API 调用**。

### 最终体检结果（`tools/final_check.py`）
- ✅ **硬替换体检：20/20 全部通过**（所有 hard_replace 术语的期望译名都出现在译文里）
- ✅ `hard_replace` 类改动：**最坏 0 段失效**（20 条全部 0 成本）
- ✅ `prompt_hint` 类改动：只影响命中段（`retrieval stopping` 43 段 / `transdiagnostic` 3 段 / `SIF` 14 段）
- ✅ 测试 14/14 通过

### 教训（值得记住）
1. **静默失败最可怕**：Bug 1（规则形同虚设）和 Bug 3（悄悄删内容）都不报错，只有体检能抓到
2. **"删除冗余"类规则必须带条件**：无条件删除一定会吃掉唯一的信息载体
3. **测试运行器也可能害你**：我给测试结果打印加了 emoji，在 GBK 控制台下把失败信息本身搞崩了，

### ⚠️ QA 工具自身的 bug（重要教训）
**一个会产生假警报的检查器，比没有检查器更糟** —— 它会消耗你的注意力去查不存在的问题。
初版 QA 报了 47 处"数字丢失"，逐条核实后发现**全是误报**：
- **`\w` 在 Python 里匹配汉字**！`(?<![\w.])(\d+)` 遇到「高达81%」时，81 前面是汉字 → lookbehind 失败 → 数字没被识别。
  必须显式写 `[A-Za-z0-9.]`。这一条修完，数字丢失从 16/113 降到 1/113。
- 前缀残留判定太宽：`iPSC`（诱导多能干细胞）的 `i` 是名字的一部分，被当成方位前缀误报。
  改为「前缀必须是已知方位字母**且**后面那截在术语表里有条目」。
- 报告里只写"段 01" → **多个节都有 #01**，无法定位。改为打印节路径 + 段序号。

### 本轮修掉的两个真 bug（都很危险）

**① 缩写的匹配必须大小写敏感** ⭐
为支持 `aDLPFC` 我加了"可选小写前缀 + 忽略大小写"，后果：
```
'flares' 被匹配成 LAR   ->  前缀 f + lar + 复数后缀 es
'fibs'   会被匹配成 IBS
```
后果是**静默错误命中**：硬替换体检报假失败；若换成应用替换还会污染译文。
→ 修法：缩写（`^[A-Z][A-Za-z0-9]{0,7}$`）的核心**必须大小写敏感**，只允许小写方位前缀；
  复数后缀从 `(?:e?s)?` 收窄为 `s?`。
  验证：`flares`→否、`fibs`→否、`LAR`/`LARs`/`aLAR`/`aDLPFC`→是 ✓
  效果：s41575 的「hard_replace 未落地」从 1 条 → **0 条**。

**② 段落 ID 撞车（静默覆盖）** ⭐
实测 s41574 有 **36 段但只有 35 个唯一 sid** —— 两段的 sid 与原文完全相同。
若不处理，dict 会静默覆盖：**缓存、译文产物、音频定位三者一起去掉一段，且不报错**。
→ 修法：`_build` 里记 `seen_sids`，重复则加 `-dup2` 后缀。

## 核心矛盾（本次最重要的判断）

**用户想要的三件事互相撕扯，这是三角约束，不是"再努力一点"能解决的：**

1. **详细介绍全文**（信息完整，Nature Reviews 一篇 8000–10000 词）
2. **不枯燥**（可听性）
3. **音频媒介的物理限制**（线性、不能跳读、不能看图、听漏了不能回看）

- NotebookLM 只挑几个点，**不是偷懒，是播客媒介的容量极限**：双人对话 15 分钟 ≈ 2000 字口语，装不下 8000 词的综述。
- 若为了"详细"把音频拉到 60–90 分钟 → 又回到"枯燥"。
- 所以纯音频形态下，**这三者最多同时满足两个**。

**建议的破局方向（候选 E）：不做"播客"，做"带原文的分层伴读"**
- **分层**：① 骨架导读 10–15 分钟（讲清这篇综述在争论什么、给了什么框架、结论是什么）；② 分节精讲 每节 3–6 分钟（按 `Sec1/Sec2…` 切，可单独听、可跳、可重复听）。
- **讲解稿 = LLM 按段重写**：不是翻译、不是朗读，而是"讲人话但讲全"（保留每段信息点；术语首次出现给英文 + 一句解释）。
- **音频↔原文定位不只是导航，它是让 1+2 同时成立的机制**：因为听漏能立刻看原文，所以敢用高信息密度的讲稿；还能顺带做"每段首句"的速览音轨。
- 形态：本地网页播放器，左侧音频、右侧原文，段落高亮随播放走，点段落跳音频。

## 假设翻转

- **"网页抓正文比 PDF 更干净"** → 用户原本的假设。实测：**网页路线恰好缺了段落级 id**（`Par{n}` 计数为 0），
  而这正是"音频↔原文定位"最需要的东西。**GROBID 输出的 TEI 反而带段落标签 + PDF 坐标** → 结论反转，PDF 路线更优。
- **"只做 Nature Reviews，所以可选文献很少"** → 若把范围放宽到 CC BY 的完全 OA 刊（Nature Communications / Scientific Reports / BMC / npj），
  同样级别、同样能听，还完全合法。对"只自己用"不是必要，但**建议保留这个后路**。

## 闪念

- 音频的"可追溯性"是最强差异化点，且**连 NotebookLM 都没做**（它的文本问答能跳引用，音频不能）。

### 关键教训（新增两条通用规律）

**A. 「存在即算」类判据必须换成「按量主导」**
`any(字体在行内)` → 一行里只要有一个正文字体的 span，整行就算正文。
正确做法：**按字符数算主导字体**。同类问题在 `_detect_layout` 里也有
（`for f in L.fonts: fam[f] += len(L.text)` 把整行长度重复计给每一种字体）。
→ 通用规律：**判"这行属于哪一类"时，永远看主导成分，不看是否存在。**

**B. 首页要做例外**
页面装饰面板（首页大矩形）与 Box 在几何上无法区分，但**语义上相反**：
首页面板里装的是标题和摘要（要保留），Box 里装的是框图（要排除）。
→ 规则：`in_region = in_rect and 主导字体 ≠ 正文 and page > 0`

### 顺带修掉的排版错误
**数字千分位用了全角逗号**：LLM 写出 `2，373`。中文排版规范要求半角；
更实际的问题是 **TTS 会把全角逗号读成停顿** → `2，373` 读成"二，三百七十三"，数字读错。
→ 新增 `src/textnorm.py`（后处理层，**不进缓存**，改动永远零 API 成本）。
限定「后面正好 3 位数字」以免误伤 `第一，第二`、`1，2，3`。

## 用户新需求：译文 ↔ 原文同步滚动（对照阅读）

**用户原话**：*"说到对照原文阅读，我就希望有另一个功能了，就是译文和原文同步滚动，这部分有好的实现办法吗"*

### ⭐ 我的判断（先翻假设）

**「同步滚动」是在弥补「我们无法控制版面」的缺陷 —— 但这里版面恰恰是我们自己生成的。**
所以不必去模拟对齐，**可以直接把对齐做进结构里**。三条路线：

| 路线 | 做法 | 成本 | 对齐质量 |
|---|---|---|---|
| **A. 交错双语** | 英文段紧跟中文段（同一文件） | **5 分钟、0 代码** | **完美**（结构决定） |
| **B. 自建双栏 HTML** | 从现有 JSON 生成自包含 HTML，双栏 + 锚点同步 | ~1 小时 | 好（可在段内按比例） |
| **C. VS Code 双编辑器** | 左右两栏打开 en.md / zh.md | 0 | **不可行** |

**C 已查证排除** ✅：VS Code 只同步**同一文件**的 editor ↔ preview
（`markdown.preview.scrollPreviewWithEditor` / `scrollEditorWithPreview`），
**两个不同编辑器之间没有滚动同步**。所以别指望白嫖。

### 技术要点：朴素的"按比例同步"一定会难看

中文与英文的**段落高度差很大**（同样内容，中文换行数通常少 20–30%，
但段落间差异不均等），按 `scrollTop / scrollHeight` 比例同步 → 越读越漂。

正确算法是**混合式**：
1. 取当前视口顶部第一个可见段落 A，记它在视口内的偏移 `dy`
2. 在另一侧找**同一个 sid** 的段落 B（sid 我们本来就有，就是 `<-- sid -->` 锚点）
3. `B.scrollTop = B.offsetTop - dy`
4. **段内剩余部分按高度比例分配**

→ 段落高度差被吸收在**一个段落范围内**，不会累积漂移。需要一个 `isSyncing` 标志防回环。

### 更重要的反转：真正让你累的不是"视口不对齐"

是**找到对应段落**。滚动同步只解决"大致在同一位置"，
但段落高度不等时，眼睛仍要在两侧自己找配对。
→ **配对高亮**（点/悬停一侧段落，另一侧同 sid 段落高亮）比滚动同步更直接地解决问题，
而且它让滚动同步的精度要求大幅下降。两个都做最省力。

### 与已有设计的衔接
- 锚点现成：`data/translation/<doc>.json` 里每段有 `src` + `zh` + `sid`，不需要重新解析 PDF
- **音频定位可以复用同一套锚点** → 「左音频 / 中译文 / 右原文」三栏，
  播放到哪段就三段一起高亮 + 自动滚动。这是"音频↔原文定位"的自然落点
- 这也是**建议用浏览器页面而不是 VS Code 扩展**的理由：`<audio>` + onclick 跳时间戳在网页里是十行代码

### 风险 / 会死在哪
1. ❗**对齐粒度**：sid = 段落。一段 300 词时，段内对齐是猜的。
   要做句级对齐需额外一遍 LLM 或专门的句子对齐算法（**先别做**）
2. ❗**自建阅读器的经典陷阱**：花两小时做的阅读器可能不如"交错 md + 编辑器"好用。
   → 所以**先做路线 A（5 分钟）**，不够再上 B
3. ⚠️ 双栏在笔记本上每段只能看到 3 行左右，可能反而更难读 → 需要**布局可切换**（双栏 ↔ 交错），
   而 CSS class 切换几乎不增加成本，让用户自己试

## 截断标题的真实成因：插桩查实，四个机制（不是猜的）

**方法**：先插桩打印「每个 run-in 标题是由哪一行产生的 + 它的物理前一行」，
再动手改。前几轮我一直在凭现象推测，这次证明**插桩是必须的——真实成因和我猜的完全不一样**。

| # | 机制 | 实例 | 证据 |
|---|---|---|---|
| A | run-in 标题**断在连字符**上 | `dative stress.` / `tent fasting.` | 前一行 `…and oxi-`、`…stopping intermit-`，结尾 `-` |
| B | **图注跨行续行**被当标题 | `receptive anal intercourse.` / `anal cancer.a` | 字号 **7.0pt**（图注）vs 正文 8.2pt；前一行是 `Fig. 6 \| …` |
| C | **表注跨行续行**被当 h2 | `treatment-related problematic RAI` / `problematic RAI` | 前一行是 `Table 2 \| …` / `Table 3 \| …`，同字号同字体 |
| D | 标题**断在普通空格**上 | `related disorders.` / `and related disorders.`（vieta2018） | 前一整行加粗 `Other specified bipolar and unspecified bipolar and` |
| E | **图内面板标签**被当 h2 | `a  Surgery` / `c  Systemic treatment` | `^单字母+空格+标题`，字号大于正文 |

**我事先只猜到了 A。** B/C/D/E 全是插桩才暴露的。

### 对应修法
- **A+D 合并**：`_runin_head()` —— 只要**上一整行仍是"未被识别的整行加粗"**（`kind=="other"`），
  就继续往前接，最多 3 行；护栏是"上一行不能以句末标点收尾"。
  `_join()` 自动处理断词（连字符去掉、空格保留）。
- **B+C**：新增 `is_caption_cont` —— 上一行已被判为图注，且本行与它**同字号同字体** → 本行是图注续行。
- **C 的另一半**：run-in 字号下限从 `|sz-bs| ≤ 1.5` 改为 `(bs-0.2) ≤ sz ≤ (bs+1.5)` ——
  **小标题不可能比正文还小**，7.0pt 的图注因此被排除。
- **E**：`PANEL_LABEL_RE = ^[a-h]\s{2,}\S` 且字号 > 正文 → 图内面板标签。
- 附带：`new_section` 里剥掉标题尾部图板字母（`anal cancer.a` → `anal cancer`）。

### ⚠️ 我讲解时说错了两处（先记下来，这比结论更该留）

| 我说过 | 实际 |

### 真实机制（打印数据之后才看明白）

```
term=SIF   zh='SIF（压抑诱发的遗忘）'   mode=prompt_hint   full_en=suppression-induced forgetting
```

`render_prompt_block` 把它渲染成：

```
- SIF -> 「SIF（压抑诱发的遗忘）」（缩写首次出现时给全称…之后可直接用 SIF）
```

**这句话本身就是最强指令** —— 字面意思就是"把 SIF 译成这一串"。
`note` 里其实**已经写明了**"首次给全称、之后用 SIF"，但**弱提醒敌不过 `zh` 的字面写法**，
于是 LLM 在句子里整串照抄：`…以 SIF（压抑诱发的遗忘）衡量…`，全篇 24 处里 12 处如此。

同一段里正好能看清两种机制各自在做什么（很好的教学样本）：

```
LLM 原始: …aDLPFC 和 VLPFC …（以 SIF（压抑诱发的遗忘）衡量）和动作停止（以停止信号反应时（SSRT）衡量）
硬替换后: …前部背外侧前额叶 和 腹外侧前额叶 …（以 SIF（压抑诱发的遗忘）衡量）和动作停止（以停止信号反应时 衡量）
```

- `aDLPFC` → 中文：**`hard_replace`** 干的（程序替换）
- `（SSRT）` 被删：**`_fix_parenthetical`** 干的（去冗余）
- `SIF（压抑诱发的遗忘）` **一字未动**：LLM 自己就这么写的

### 通用规律（新增，值得记住）

**`zh` 字段的语义是"译名"，不是"译名＋解释"。**
写进 `zh` 的任何东西都会被当成"该术语的标准写法"整串照抄到句子里。
解释要放 `note` —— `note` 的注释本来就写着"对 LLM 的说明（仅 prompt_hint 有意义）"。

这正好是"能用字符串替换解决的绝不调 LLM"的**反面**：
这里**字符串替换表达不了"首次出现给全称、之后用缩写"**，只能靠 prompt 约束，
而 prompt 约束又必须"译名与解释分家"才生效。

- **时间轴累计漂移 Bug 定位与修复（2026-09-20，重大工程经验）**：
  - 故障现象：用户反馈在 27:45 左右，页面显示为第 24 段（“胃肠道方面的疾病...”），但实际音频播放的是第 20 段的内容，整篇时间轴出现明显累计漂移。
  - 根因排查（实测定位）：
    1. 早期静音帧格式错配：此前插入的静音帧为 MPEG-1 Layer 3 (44.1kHz)，而 Edge-TTS 输出的是 MPEG-2 Layer 3 (24kHz Mono 48kbps)。采样率头不匹配导致解码器解码静音时时长被拉长。
    2. 计算口径差异：此前单段时长以 `SentenceBoundary` 最后一句话的结束点计算，忽略了 MP3 编码的尾部 Padding（每段相差约 0.05s），109 段累计漂移达 56.5 秒。
  - 修复方案：
    1. 采用与 Edge-TTS 编码完全一致的 24kHz 48kbps MPEG-2 Layer 3 标准静音帧 (`\xff\xf3\x64\xc4`)。
    2. 单段时长直接基于真实生成的 MP3 比特流物理帧长精确计算。
  - 实测验证结果：
    - 7024.728 秒全长 MP3 比特流时长与时间戳累加值完全一致，**2 小时音频累计漂移降至 0.0 毫秒**。
- **逐句卡拉OK级变色高亮（2026-09-20）**：
  - 技术实现：利用此前在 `timestamps.json` 中保存的 `SentenceBoundary` 毫秒级边界，将讲稿切分为带 `data-start` / `data-end` 的 `span` 元素。
  - 联动效果：播放时当前段落保持聚焦，正在朗读的**那一句中文**实时呈现蓝色荧光胶囊高亮并随音频流动；点击页面上任意单独一句话即可瞬间精准跳至该句起点播放。
- **移动端 (Android / iOS 手机浏览器) 响应式体验重构（2026-09-20）**：
  - 用户反馈痛点：① 电脑端 UI 满意，但在手机浏览器上，底部浮动播放器各种按钮与文本堆挤在一起；② 顶部导航栏单行容纳过多元素导致按键狭窄、容易误触。
  - 响应式优化方案（采用标准双端自适应布局，电脑端完全保留，移动端针对大拇指交互重构）：

    2. **底部悬浮播放器（手机端）**：
       - 第 1 行：左侧显示当前章节标题与播放时间戳，右侧紧凑集成「跟随」与「倍速」选择器；
       - 第 2 行：全宽触摸进度拖拽条（Seekbar）；
       - 第 3 行：居中放置三个大号触控按钮（`⏪ 15s`、`50px 主播放键`、`⏩ 15s`），间距扩大至 28px，彻底解决按键挤成一团的问题。
    3. **桌面端（PC / iPad 大屏）**：通过 CSS Grid 精准还原原来的单行控制台（左控制键 / 中标题与时间 / 右工具项 / 下进度条），桌面交互体验零损失。
    4. **移动端适配增强**：加入 `viewport-fit=cover` 与 `env(safe-area-inset-bottom)`，完美适配带手势底条的现代 Android / iOS 全面屏手机。
    5. **播放栏文字极致精简**：根据用户建议，将播放栏标题统一精简为纯粹的 **`第 X 段`**（如 `第 1 段`、`第 24 段`），彻底消灭多余文本，无论屏幕多窄都绝不超界或挤压。
