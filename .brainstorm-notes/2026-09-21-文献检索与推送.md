## 用户原话（目标）

> 接下来我们来扩展我们的工作流，我希望把文章检索也加进去。现在我搜索文献的方法是在 PubMed 里
> 搜索 `"Nat Rev*"[jour]`，我希望可以做一个推送程序，当我运行这个程序时为我推送按时间排序的
> 搜索结果、中文翻译，如果有 Abstract 的也显示出来。

## 背景 / 约束（沿用主项目）

- **只自己用**；三条红线：① 任何"向公众提供" ② 全文进第三方云服务 ③ 绕过付费墙。
  → 本议题只涉及**题录 + 摘要**（非全文），不绕过付费墙，风险等级**低于**主项目。
- 用户方向：精神科 / 神经科学 / 内分泌（已有 4 篇：双相障碍、侵入性思维、肥胖内分泌、精神科文化）。
- PubMed E-utilities **无需 API key**（限 3 req/s），本机**可直连**（已实测）。

## 用户决定（2026-09-21 已确认）

1. **终点**：从 digest 里**选出一篇**送进现有工作流生成语音。
   但「**找到文章 → 获取 PDF**」这一步**必须经由第三方、无法脚本化**，
   用户暂时没想好怎么把两端连起来。→ **这成为本次最核心的设计问题。**
2. **期刊范围**：**凡是 `Nat Rev` 开头的全要**，不做期刊过滤。
   → 原建议"按与用户方向的相关度排序"已被否；排序维持**按时间**。
3. **一句话提要**：✅ 采纳（即下方 R2）。

## 查证发现（2026-09-21 · 全部为**实测**，非估算）

### 1. `"Nat Rev*"[jour]` 的真实体量（✅ `scratch/pubmed_probe.py`）

| 时间窗 | 条数 |
|---|---|
| 近 7 天 | 42 |
| 近 30 天 | 177 |
| 近 90 天 | **566**（≈ **44 条/周**） |
| 全部 | 49,779 |

近 90 天覆盖 **18 个期刊**。其中含 `Nature reviews. Chemistry`（32 条/90天）、
`Nature reviews bioengineering`（5 条）等**与用户方向无关**的刊
→ `Nat Rev*[jour]` 对个人医学生物学阅读**偏宽**，混着化学/工程类内容。

### 2. 🔴 关键发现：61% 条目**没有摘要**，且「有摘要」≈「是综述」（✅ `scratch/pubmed_probe2.py`）

近 90 天 566 条的交叉表：

|  | 带 `Review` 标签 | 不带 `Review` 标签 |
|---|---|---|
| **有摘要** | 204 | 5 |
| **无摘要** | **0** | 357 |

- 无摘要的 357 条 = Research Highlight / News / Published Erratum / Interview / Editorial。
  样例：`The many faces of malaria parasites.`、`The value of speed for drug developers.`、
  `Publisher Correction: …`（这些**不是综述**，正是它们在污染列表）。
- 「有摘要」与「带 `Review` 标签」**重合度 98%**（204 / 209），两个判据几乎等价。

→ 用户那句"**如果有 Abstract 的也显示出来**"**不只是显示过滤，而是一个近乎完美的判别器**：
  566 → 209 条（**44 → 16.3 条/周**）。

### 3. 过滤策略实测对比

| 策略 | 条/90天 | 条/周 |
|---|---|---|
| 不过滤 | 566 | 44.0 |
| 只要有摘要 | 209 | 16.3 |
| 只要 `Review` 标签 | 204 | 15.9 |
| 有摘要 且 摘要 > 800 字符 | 203 | 15.8 |

推荐口径平均摘要 **1361 字符 ≈ 209 英文词**。
→ **全译所有摘要 ≈ 3,307 英文词/周**，仅相当于**半篇**综述（主项目单篇 5,000–11,000 词）。
**翻译成本不构成约束**（推翻了"体量爆炸"的担心）。

### 4. ⚠️ 排序陷阱（✅ `scratch/pubmed_probe3.py`）

| `sort` 参数 | 实测行为 |
|---|---|
| **不传（默认）** | **已经是"最新在前"**（等价 `edat`） |
| `sort=edat` / `sort=date` | 最新在前，与默认一致 |
| `sort=pub_date` | **另一种顺序**，首批 PMID 反而更小（新入库的被挤下去） |
| `sort=relevance` | 乱序 ❌ |

→ "按时间排序"**不需要传 `sort`**；而最像正解的 `sort=pub_date` **恰恰是个坑**
（静默给出错的顺序）。这正是本项目最忌讳的"静默错误"类型。

### 5. 竞品（✅ 已访问官网）——**必须承认这一层已被覆盖**

- **领研 LinkResearcher**（✅ 官网首页）：有 **论文订阅 + 期刊订阅**、中文标题 +
  **中文一句话导读**（例：「华科大刘刚团队新发现：糖尿病确诊前，血管损伤信号已出现？
  这两个血糖值很关键！」，来源 *Metabolism*）、**音频导读·科学60秒**（单条 12–14 分钟）、
  一周论文排行。→ 用户描述的功能**基本被覆盖，且已做到音频形态。**
- **文献鸟 Stork**（✅ 官网首页；此前调研已确认更强）：「文献追踪、阅读、翻译」，
  已有「听文献」付费功能与「PDF → 双人对话音频」。
- **PubMed 官方**：MyNCBI saved search 邮件提醒 + RSS（`/rss/search/<query>/`）
  → **检索与推送本身早被官方覆盖，只缺中文。**
- ❓ 未取到：领研/文献鸟可否**按刊订阅**、是否免费、翻译是否可用自定义术语表。

### 6. 🔑 DOI 覆盖率 100% —— 断点其实可以从两侧接上（✅ `scratch/pubmed_probe4.py`）

近 90 天 204 条有摘要的条目：**带 DOI 204 条（100%）**，且**全部前缀都是 `10.1038`**。
DOI 后缀与现有 `doc_id` 命名规则（`doc_id = pdf.stem`）**完全一致**，已交叉验证：

| PubMed 期刊 | DOI | doc_id 候选 |
|---|---|---|
| Nature reviews. Nephrology | `10.1038/s41581-026-01131-8` | `s41581-026-01131-8` |
| Nature reviews. Endocrinology | `10.1038/s41574-026-01301-5` | `s41574-026-01301-5` |
| Nature reviews. Immunology | `10.1038/s41577-026-01354-7` | `s41577-026-01354-7` |
| Nature reviews. Molecular cell biology | `10.1038/s41580-026-01026-3` | `s41580-026-01026-3` |

**关键交叉验证**：用户本地已有 `papers/s41574-022-00638-x.pdf`
（Nature Reviews Endocrinology，间歇性禁食/肥胖）→ **前缀 `s41574` 与上表完全吐合**。

→ **本次设计的枢纽推论**：
> digest **不需要拿到 PDF**。`doc_id` 完全由 DOI 决定，而 DOI 在题录里 100% 可得。
> 所以 digest 可以在用户**还没下载 PDF 之前**，就把**将来要跑的确切命令**准备好。
> 「断点」不是要消灭的，而是要**在两侧各放一个落点**。

### 7. PDF 里能抽出 DOI（决定"手工下载 → 丢进 inbox 自动认领"是否可行）

✅ 实测 4 份本地 PDF（抽前两页文本）：

| 文件 | stem | 抽到的 DOI | 是否命中 stem |
|---|---|---|---|
| `s41583-025-00929-y.pdf` | `s41583-025-00929-y` | `10.1038/s41583-025-00929-y` | ✅ |
| `s41575-024-00932-1.pdf` | `s41575-024-00932-1` | `10.1038/s41575-024-00932-1` | ✅ |
| `vieta2018.pdf` | `vieta2018` | `10.1038/nrdp.2018.8` | ❌（手工命名，不符规则） |
| `s41574-022-00638-x.pdf` | `s41574-022-00638-x` | 未抽到 | ❌（首页文字层异常） |

→ 3/4 可行；不可行的可**用标题模糊匹配兜底**（PDF 首页文字 vs feed 里的标题）。

### 8. 附带事实：几乎全部 Nature Reviews 综述都不在 PMC

204 条里带 `pmc` id 的只有 **3 条**（id 类型计数：`doi` 204 / `pii` 204 / `pubmed` 204 / `pmc` 3 / `mid` 3）。
→ "自动获取全文"这条路对 Nature Reviews **基本走不通**，进一步说明
**human-in-the-loop**（用户手工取 PDF）是**正确形态**，而非妥协。
（❓ 未验证：有 PMC id ≠ 一定有 OA 全文，可能只是作者稿。）

### ⚠️ 本次我自己的解析 bug（差点报出假结论）

首次跑 `pubmed_probe4.py` 时，我用 `.//ArticleId` 取 DOI，拿到的是**参考文献**的 DOI
（`ReferenceList` 里同样有 `ArticleIdList`，而字典**后写覆盖先写**）。
表现为：*Nature Reviews Nephrology* 的文章配上了 `10.1038/ki.2010.169`、
*Nature Reviews Immunology* 配上了 `10.1016/j.cell.2020.09.062`。
**是"数据看起来太荒谬"暴露了它**，否则我会把错误结果当 100% 覆盖率报给用户。
→ 教训：**XML 解析一律限定到本条目自己的容器**（`PubmedData/ArticleIdList/ArticleId`），
不要用 `.//` 跨层；**检查器的判据本身要先验证**（项目第 6 次同类教训）。

## ⚠️ 本轮我犯的三个错（都是"不报错、只出错"的那类）

1. **`field` 字段名遮蔽了 `dataclasses.field`**
   `field: str = ""` 之后，同一类体里的 `field(default_factory=list)` 变成对字符串的调用
   → `TypeError: 'str' object is not callable`。已改名 `term_field` 并加注释防止被改回去。
2. **快照按文件名排序会取错期**
   `sorted()` 里 `-`(0x2D) < `.`(0x2E)，于是 `2026-09-21-0843.json` 排在
   `2026-09-21.json` **前面**，取最后一个反而拿到**旧的那期**。
   症状：手机上打开的是 A 期，`--pick 3` 却指到 B 期的第 3 条 —— **不报错，只跑错文献**。
   → 改为按快照内部 `generated_at` 排序；已写回归测试，且该测试会**反过来断言
   文件名排序确实是错的**，以证明测试本身有意义。
3. **用 `len()` 当长度判据是错的**（第 7 次"检查器的判据本身要先验证"）
   `BRCA1-BARD1 与 53BP1 轴拮抗决定 HR 或 NHEJ 的选择。` 的 `len()` 是 **40**，
   读起来只有 **15** 个字。用 `len()` 会把这种**很好**的 brief 误判为超标。
   → 加 `reading_len()`，口径与 prompt 里"缩写算 1 个字"一致。
   → 附带教训：修这个 bug 时**我又手数一遍长度并数错（说 33，实际 40）**，
     最后靠直接打印才对。**说数字前先打印，没有例外。**

## 推送层（2026-09-21 已完成）

**新增**：`src/push.py`（渠道注册表 + 三个 sender）、`tools/push_digest.py`（独立入口）、
`tests/test_push.py`（14 个离线测试，不联网）；`build_digest.py` 加 `--push`。

**渠道**：`wechat`（PushPlus）/ `telegram` / `discord`，**可单选可多选**，
`all` = 所有已配置的。配置全在 `.env`（已写进 `.env.example`）：
`PUSHPLUS_TOKEN`（可选 `PUSHPLUS_TOPIC`）、`TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID`、
`DISCORD_WEBHOOK_URL`（或 `DISCORD_BOT_TOKEN` + `DISCORD_CHANNEL_ID`）。

**三个设计决定（都写进代码注释了）**
1. **推内容，不推链接** —— digest 页是单文件自包含 HTML、**没有 URL**，链接发出去手机打不开。
2. **一律纯文本，不用 Markdown/HTML** —— Telegram 的 MarkdownV2 要转义
   ``_*[]()~`>#+-=|{}.!``，漏一个就整条失败；Discord 用自己的 md；PushPlus 走 md 模板。
   三套规则互不兼容 → 统一纯文本，**从根上消灭“转义漏字符”这类 bug**，代价只是没有加粗。
3. **微信不刷屏**：`POLICY["wechat"]["max_messages"] = 1`，条目多时只发第一条
   并**明确说明还有多少条没发**（Telegram / Discord 是频道，可以多发）。

**PushPlus 接口注意事项**（✅ 已核对官方文档 V1.18）
- `POST https://www.pushplus.plus/send`，body 是 `token/title/content/template`。
- ⚠️ **`code=200` 只代表服务端收到请求**，不代表送达（接口是异步的，
  最终结果要凭 `data` 里的流水号查）。所以代码只能确认“已提交”，注释里写明了这点。
- `template=markdown`；`topic` 是群组编码；不填 `option` 时发给自己。

**本轮我又犯的三个错**
- **测试断言写错**：把 `"telegram discord"`（空格分隔 = **两个**渠道）当成一个渠道。
  **实现是对的、测试是错的** —— 按纪律先打印实际值才定位到。
- **通知标题与正文对不上**：标题写 `snap['count']`（65），正文却只发 `--limit 3` 条。
  已改为用 limit 之后的**实际**条数。
- **`--list-channels` 用 `:<22` 对齐中英混排** → 中文按字符数补齐、显示宽度却是两倍，挤在一起。
  改成一行只放一个字段。

**端到端验证**：四条路径都实测过（单选 / 多选 / `all` 跳过未配置 / 报错），
全部用 `--dry-run`（**没有真的发出任何消息**）。

### 微信详情页的排版（✅ 已实测，用户实际收到并确认）

**可用能力**：内联 `style` **全部生效** —— 蓝色序号、`border-bottom` 分隔线、灰色小字都在。
所以微信渠道可以用 `template=html` 做真正的排版（`PUSHPLUS_TEMPLATE` 可切回 markdown/txt）。

**关键约束**：微信渠道内容上限 **2 万字**（免费；会员 10 万）。
这直接决定排版能做多细 —— 下表全是实测值（65 条）：

| 布局 | 全长 | 结果 |
|---|---|---|
| 序号 + 提要（第一版，每条 4 个带 style 的标签） | ~28,000 | ❌ **超限，丢条目** |
| 序号 + 提要（压紧成每条 1 个 `<p>`） | 15,013 | ✅ 有余量 |
| **序号 + 标题 / 简介 / 期刊·日期·DOI**（用户要的） | **18,579** | ✅ 刚好压线（98%） |
| 同上 + `detail` | 被截断 | ❌ **`detail` 在微信里放不进去** |

**教训**：内联样式是"每条都要重写一遍"的成本。第一版单条 430 字里 **90% 是 markup**，
实际内容只有 40 字。**所以每加一个字段前必须先量长度**，而不是发出去才发现被截断 ——
微信的截断是静默丢条目，只在末尾留一行小字。

**`<style>` 块：已实测可用** ✅（2026-09-21）

用一条橙底"排版自检"探针实测确认：**PushPlus 完整保留了 `<style>` 块 + class**。
探针本身是可复用的手法 —— 想验证"某个 HTML 特性还在不在"时，
在消息顶部插一行用该特性渲染的自检行，用户一眼就能判断，比让他描述"看起来对不对"可靠得多。
（探针已在 `src/push.py` 里保留为 `PROBE_STYLE`，默认关闭。）

于是排版改成双模式，**共用同一份 `_HTML_STYLES`**，只改样式的挂载方式：
- `html`（默认）→ `<style>` 块 + class，markup 约省四成
- `html-inline` → 逐元素内联，保底方案

实测容量对比（带 `detail`）：

| 条数 | `html`（`<style>` 块） | `html-inline`（内联） |
|---|---|---|
| 11 条 | 5,671 字（30%） | 7,948 字（42%） |
| 25 条 | 11,551 字（61%） | 17,342 字（91%） |
| 40 条 | **18,019 字（95%）可容纳** | 超出上限 ❌ |

→ **css 模式把容量翻倍**，因为内联样式是"每条都要重写一遍"的成本。

DOI 已确认在微信里**可以点击跳转**（用户实测）。

#### ⚠️ `cmd.exe /c` 的引号坑（已实测复现）

为给任务加输出重定向，我改成了
`cmd.exe /c "...python.exe" "...build_digest.py" ... >> "...log" 2>&1`。
**结果任务返回 1，日志文件根本没生成。**

原因（用 `subprocess` 传原始命令行字符串复现确认）：
**`cmd.exe` 的 `/c` 在引号多于两个时会剥掉首尾引号。**

```
cmd /c "<解释器路径>" "tools\build_digest.py" --help
                 ↓ 剥掉第一个引号 + 最后一个引号
<解释器路径>"  "tools\build_digest.py --help
     ↑ 可执行文件名多了个尾部引号 → 找不到 → exit 1，且不生成任何文件
```

对照实验：无引号 / 2 个引号 ✅ 正常；4 个以上引号 ❌ 失败。**症状与线上完全一致。**

→ **教训：不要在任务计划的 `Arguments` 里塞 shell 和重定向。**
正确做法是**让工具自己写日志**，于是任务参数可以全是相对路径，也不需要 shell。

### ⚠️ `--days` 的语义（很容易搞反，写给未来的自己）

**`--days` 是"回看窗口"，不是"推送范围"。** 推送范围由状态库决定（只推 `new`）。
所以**每周脚本应该写 `--days 30`**：万一漏跑一周，下次仍能捞回来；状态库保证不重复推。
把窗口写成 `7` 反而会在漏跑时**永久丢掉**中间那几天。
